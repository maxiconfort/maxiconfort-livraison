# Projet : App Livraison Pro (livraison.maxiconfort.fr)

PWA interne de gestion des livraisons Maxiconfort. **Ce dossier est le repo git actif** (GitHub `maxiconfort/maxiconfort-livraison`, déployé via GitHub Pages + CNAME).

## Stack
- App mono-fichier : `maxiconfort-v7.html` (~13 000 lignes, HTML/CSS/JS vanilla)
- Backend : Supabase projet `jmvfjtnmebstkzcfnlgp` (RLS x-app-secret, Edge Functions, pg_cron)
- SMS : Brevo · Cartes : Leaflet/OSRM · PWA : `service-worker.js` (**toujours bumper CACHE_VERSION à chaque déploiement du HTML**)
- Credentials : `.env` (jamais commit) · Déploiement Edge Functions autonome via token Supabase PAT (`SUPABASE_ACCESS_TOKEN` puis `npx supabase functions deploy <nom> --project-ref jmvfjtnmebstkzcfnlgp --no-verify-jwt`)

- **PIN admin = base source de vérité (v7.5.52)** : changer un PIN en base (table `parametres`, ex `pin_admin`) n'avait AUCUN effet sur le login. Cause : (1) l'écran de login lit `localStorage.getItem('pin_admin') || '1234'` au démarrage (clé jamais écrite → toujours `1234`) ; (2) `sbLoadParametres()` (qui lit le PIN en base) ne tournait que dans `buildUI()`, soit APRÈS le login ; (3) `savePin()` n'écrivait qu'en localStorage, jamais en base. Les deux systèmes (local vs base) étaient déconnectés. Correctifs : `sbLoadParametres` appelé au `DOMContentLoaded` (avant login) + écrit les clés `localStorage.pin_admin/collab/livreur` (instant au prochain démarrage) ; `savePin` fait aussi `sbSaveParametre('pin_'+r, v)` (propagation cross-device) ; déblocage d'urgence SAS (`sasDeblocageAdmin`) utilise `PINS.admin` au lieu de `1234` en dur. Testé : appareil neuf (localStorage vidé) → PINS.admin=0402 au démarrage, livreur reste 9012. **PIN admin actuel = `0402`** (collab 5678, livreur 9012).
- **Polling encaissement fiable (v7.5.51)** : le règlement validé par le livreur (CB/Espèces/Mixte/Déjà payé) ne remontait pas en direct côté admin (page Encaissements + tournée) pour les commandes **anciennes** livrées le jour même. Cause : le polling 10 s (`startPolling`, ~ligne 3654) ne récupérait que les **50 commandes les plus récemment CRÉÉES** (`order=created_at.desc&limit=50`) — une commande passée il y a 2-3 semaines puis livrée aujourd'hui était hors fenêtre (vérifié : `#1172` livrée CB hors des 50). Correctif : tri par **`updated_at.desc.nullslast&limit=80`** → toute commande que le livreur vient de modifier remonte en tête et est rafraîchie en 10 s. Le bloc `_syncNeeded` propage ensuite `paie/stpaie` commande→stop, donc la tournée se corrige aussi. Un seul changement règle les 3 symptômes (admin, encaissement, tournée). Le canal Realtime (autre voie) mappe déjà bien `paie/stpaie/montantEnc` mais le WebSocket est instable → le polling est le filet de sécurité. `sbSaveCommande` met toujours `updated_at` (0 commande NULL en base).
